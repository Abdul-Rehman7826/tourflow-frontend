# Step 11, Section 1: Booking State APIs

The Leads conversion modal now supports draft quotations and atomic booking
confirmation with invoices, installment schedules, optional receipts and allocations.
Payment capture resets to zero whenever a saved quote is reopened.

The conversion dialog uses a compact two-column desktop grid and a single-column
mobile layout. The footer stays outside the internally scrollable form body.

## Demo Reset

Agency admins can use **Reset Test Data** in the Leads filter bar. The context
API `resetToDefaultMockData()` aliases the tenant-scoped `resetToDefaults()`:
it replaces the current agency's operational snapshot, clears converted clients,
bookings and receipts, and restores seeded tour occupancy and six fresh inquiries.
Callbacks are generated relative to the local calendar day on reset or first hydration.
Stored data is never silently replaced on reload. Authentication, settings, other
tenants and legacy recovery snapshots remain intact. The reset is browser-local;
it does not call `localStorage.clear()` or change server data.

## Context API

- `saveDraftBooking(leadId, conversion, milestones)`: saves or replaces a lead's
  quotation without converting the lead, creating a permanent client, posting
  payments or allocating seats. Lead quotes have an empty `clientId` and retain
  `quoteConversion` until confirmation.
- `confirmBookingTransaction(leadId, conversion, milestones, token?)`: context
  alias for `convertLeadToBooking`. Reuses an existing lead quote's ID and number.

- `bookings`: authenticated, tenant-scoped records. Tour managers see group-tour
  bookings; visa consultants see visa bookings. Platform owners see none.
- `createBooking({ clientId, milestones })`: creates a draft from an existing
  client's saved conversion. It does not issue an invoice, take payment, or
  reserve seats. Use this for clients converted before Step 11.
- `confirmBooking(id, token?)`: confirms a draft, creates its invoice and
  operational allocation, and optionally posts an actual payment.
- `convertLeadToBooking(leadId, conversion, milestones, token?)`: performs client
  creation, lead conversion, draft creation, confirmation, invoice creation and
  allocation in one persisted change. An invalid payment or unavailable tour
  leaves the original lead unchanged.
- `updateTraveler(bookingId, travelerId, details)`: updates the booking and linked
  passenger/visa record, deriving `isComplete` from name, passport and expiry.
  Completion is not passport-validity approval. No extra seats are reserved.
- Existing `recordPayment(...)` also updates linked booking milestones and
  passenger payment badges. Linked badges cannot be manually overwritten.

Booking creation, confirmation and payments are restricted to agency admins and
front desk. Operations roles may update travelers only for their service type.

## Inputs and Rules

Milestone input is an array of `{ name, amount, dueDate }`. Dates use `YYYY-MM-DD`
and must be in chronological order. Amounts must add up to the agreement in
integer cents. IDs and payment flags are generated by the engine.

Optional token input is `{ amount, method, paymentDate, reference? }`.
`method` uses the existing `PaymentMethod` type, including `Cash` and
`Bank Transfer`. A quoted conversion deposit never posts money automatically.

Group-tour pax and pricing come from the saved conversion. Visa conversion
currently represents one applicant, with service and embassy fees summed once.
Custom/Umrah conversion currently represents one package/traveler and a total
rate, not a per-person charge. Expanded applicant/family forms are future UI work.

Booking numbers follow `WCH-BK-XXXXXX`, sequential within each tenant. Invoice
and receipt numbers use separate sequences. Repeated confirmation and repeated
booking creation for the same active lead conversion are rejected.

Admin cancellation and refunds are described below. Completion and
confirmed-price editing are not yet exposed.

## Persistence Boundary

`tourflow_erp_v3` stores CRM, bookings, invoices, tours, passengers, visa cases and
expenses in one browser-local snapshot. Persistence succeeds before React state
is published. Migration reads `tourflow_crm_v2` and legacy ERP keys without
deleting them. After migration only the new key is authoritative.

Unreadable storage blocks mutations and displays `crmError`. A stale-tab check
requires reloading when another tab has already changed the snapshot. This is
not cross-tab locking or a multi-user database transaction. Server-side auth,
tenant authorization, database transactions and concurrency control are still
required for production. Do not treat client-side guards as data security.

## Booking Cancellation and Refunds

Agency admins can cancel confirmed bookings from the linked invoice using **Cancel Booking / Refund**. The dialog requires a reason, retention fee between zero and the total paid, refund method and explicit confirmation. Zero retention returns the full paid amount; partial retention returns the difference; retaining all paid funds issues a zero refund. Unpaid bookings may be cancelled with zero retention.

One persisted transaction marks the booking and invoice cancelled, attaches the same refund audit record to both, waives outstanding receivables, releases group-tour seats and removes active manifest allocations. Booking travelers, client profiles, original invoice amounts and receipts remain intact. Visa cases are archived out of the active pipeline. Repeated cancellations and further payments are rejected. In-progress/completed tours cannot release seats through this workflow.

Collected totals subtract refunds; cancelled invoice revenue is only the retained fee. This is browser-local accounting, not a bank/card refund integration or production server-enforced authorization. Refunds must be handled externally before recording them. The existing storage failure and stale-tab guards apply.
